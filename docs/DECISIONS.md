## Decisões técnicas do G1 (2026-10-05)

| Decisão                                                                                                         | Motivo                                                                                                                                                                               |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `trailingSlash: true` no Next + `html_handling: "force-trailing-slash"` no Cloudflare                           | Next emite `/rota/index.html`; a URL canônica passa a ter barra final (também combina com `/<ano>/`). Docs Cloudflare: `force-trailing-slash` serve `/about/` e redireciona `/about` |
| `_headers` gerado no build (`scripts/gerar-headers.mjs`), noindex global exceto com `SITE_ENV=production`       | workers.dev não pode ser indexado antes do G8. Limites: 100 regras e 2000 caracteres por linha                                                                                       |
| Cabeçalhos das respostas do Worker (`/api/*`, `/stats/*`) vêm do próprio Worker                                 | Docs Cloudflare: `_headers` NÃO se aplica a respostas geradas pelo Worker                                                                                                            |
| Next já injeta `noindex` no 404 (`/_not-found`)                                                                 | Não duplicar `robots` na página `not-found`                                                                                                                                          |
| Deploy: job `deploy` em `ci.yml`, ligado por `vars.DEPLOY_ENABLED` e secrets `CLOUDFLARE_*`                     | O usuário cria os secrets; sem eles o CI não publica                                                                                                                                 |
| `minimumReleaseAgeExclude` no `pnpm-workspace.yaml` (gerado pelo pnpm 12 para versões fixadas recém-publicadas) | Comportamento do pnpm ao fixar versões novas; revisar periodicamente                                                                                                                 |

## Umami (G5, consultado em 2026-10-05)

Fontes: <https://docs.umami.is/docs/tracker-configuration>, <https://docs.umami.is/docs/api/sending-stats>, <https://docs.umami.is/docs/environment-variables>, <https://docs.umami.is/docs/tracker-functions> e, no GitHub `umami-software/umami` (branch master, `package.json` = v3.4.0), `next.config.ts`, `src/app/api/heartbeat/route.ts` e `src/lib/ip.ts`. A versão do servidor do dono é desconhecida; a doc é da linha 3.x.

| Tema                   | Conclusão                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Atributos do script    | `data-website-id`, `data-host-url` (v2.0.0), `data-domains` (v2.0.0, compara com `location.hostname`), `data-do-not-track` (v2.17.0), `data-tag` (v2.11.0), `data-auto-track` (v2.0.0, `false` desliga o tracker e exige chamadas manuais), `data-performance` (v3.1.0), `data-exclude-search`, `data-exclude-hash`, `data-auto-pageview` (v3.2.0), `data-before-send`                                                                                                                                                                                                                      |
| `data-performance`     | Suportado desde a v3.1.0 (Core Web Vitals, enviado como `type: "performance"` ao mesmo `/api/send`). Incluído no `<UmamiScript />`. Se o servidor do dono for anterior à 3.1, o atributo é ignorado ou o envio é descartado, sem erro visível. Conferir a versão do servidor (docs/umami.md)                                                                                                                                                                                                                                                                                                |
| Nome do script         | Padrão `/script.js` (`TRACKER_SCRIPT` em `next.config.ts`). `TRACKER_SCRIPT_NAME` (env do servidor, aceita lista separada por vírgula) cria nomes alternativos. O site expõe `/stats/u.js` e o Worker busca `${UMAMI_HOST}/script.js`; só é preciso mexer se o `/script.js` do dono estiver renomeado                                                                                                                                                                                                                                                                                       |
| Endpoint de coleta     | Padrão `/api/send`. `COLLECT_API_ENDPOINT` (v1.34.0) cria um alias no servidor; o Worker chama `${UMAMI_HOST}/api/send`. Com `data-host-url="/stats"` o tracker posta em `/stats/api/send`                                                                                                                                                                                                                                                                                                                                                                                                  |
| Payload do `/api/send` | `{ type: "event" / "identify" / "performance", payload: { website, hostname, url, name?, screen?, language?, referrer?, title?, tag?, id?, data? } }`. Resposta: `cache`, `sessionId`, `visitId`. O tracker reenvia o token `cache` no cabeçalho `x-umami-cache` (conhecimento do tracker, não está na doc de API); o proxy repassa                                                                                                                                                                                                                                                         |
| Cabeçalhos exigidos    | `User-Agent` válido, senão o envio não é registrado: o proxy repassa o do visitante. Sem autenticação                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| IP do visitante        | `src/lib/ip.ts` usa `CLIENT_IP_HEADER` (se definido) e depois, em ordem: `x-umami-client-ip` (só cloud), `true-client-ip`, `cf-connecting-ip`, `fastly-client-ip`, ..., `x-real-ip`, ..., `x-forwarded-for`, `forwarded`, `x-client-ip`. O proxy envia `x-forwarded-for` e `x-real-ip` com o `cf-connecting-ip` do visitante. Se o Umami do dono estiver atrás da Cloudflare, o `cf-connecting-ip` que ele vê é o do Worker e vence na ordem: definir `CLIENT_IP_HEADER=x-forwarded-for` no servidor. A doc de "sending stats" não descreve a origem do IP; a conclusão vem do código-fonte |
| `umami.track`          | `track()`, `track(payload)`, `track(name)`, `track(name, data)`, `track(fn)`. Limites de dados: string 500 caracteres, objeto 50 propriedades, números com precisão 4. `umami.identify` existe e NÃO é usado                                                                                                                                                                                                                                                                                                                                                                                |
| Heartbeat              | `GET /api/heartbeat` responde `{ "ok": true }` (código-fonte, master). Usado por `/api/health`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
